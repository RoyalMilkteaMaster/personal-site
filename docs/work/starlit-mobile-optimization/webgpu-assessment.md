## 1. 研究問題
1. 目前各瀏覽器／裝置的 WebGPU 支援條件為何（第一手來源）？

## 2. 結論摘要
- **本輪量測到的主要瓶頸是下載量與資源準備，不是繪圖 API**：Ticket 01 4G 模擬冷載入從約 38.0 s 降到約 14.8 s，主因是傳輸量由 81.1 MB 降到 30.6 MB（拆 GLB、只載用到的切片、gzip）；WebGPU 對這部分零貢獻（量測事實＋推論，§5）。
- **沒有任何本站 WebGPU 實作或同條件比較，因此沒有可宣稱的 WebGPU 收益**。廠商的一般性效能陳述（Chrome、WebKit）不是本站量測（§7）。
- **本站渲染模型與 WebGPU 有結構性落差**：全部粒子（共用池總數隨畫布高度在 250,089–252,364 之間；手機 390 CSS px 寬視窗量測為 251,052、桌面 1440×900 為 252,364，推導見 §5.2）以 `gl.POINTS` + `gl_PointSize`／`gl_PointCoord` 畫軟邊圓點；WebGPU 的 point-list 只產生單一像素片元、WGSL 沒有 point size 內建值，遷移須改成每粒子一個實例化四邊形並重新驗證視覺等價（規格事實＋推論，§6）。
- **瀏覽器覆蓋仍不完整**：Firefox Linux／Intel Mac／Android 未啟用、Chrome Linux 僅 Intel Gen12+ 逐步推出、Android 需 12+ 且 Qualcomm／ARM（compat 模式另擴）。WebGL2 仍是唯一全平台路徑，WebGPU 只能是「第二套渲染器」而非替換（§3）。
- **建議**：不值得在此工作包規劃全面遷移。若要處理章節 morph 的主執行緒停頓，先在 WebGL2 內移除同步 `getBufferSubData` 讀回（保留 transform feedback 輸出在 GPU），並先在實機量測；這超出本票，交 Coordinator／使用者決定（§8）。

## 4. 偵測、安全情境、失敗語意與現有 WebGL2 行為

規格事實（逐字見 `ticket-05/sources/spec-quotes.txt`）：
- `navigator.gpu` 標記 `[SameObject, SecureContext]`，`GPU` 介面 `[Exposed=(Window, Worker), SecureContext]`；非安全情境下 `navigator.gpu` 不存在。[規格 §4.1](https://www.w3.org/TR/webgpu/#navigator-gpu)
- `requestAdapter()` 回 `Promise<GPUAdapter?>`，「The user agent chooses whether to return an adapter」；要求的 feature level 不被支援時「requestAdapter() will return null」。[規格 §4.2](https://www.w3.org/TR/webgpu/#gpu-interface)
- `requestDevice()` 不回 null，但「may resolve to a device which has already been lost」；裝置可隨時遺失；遺失後「No errors are generated by the device loss itself. Instead, the GPUDevice.lost promise resolves」，多數操作看似成功。[規格 §22.1](https://www.w3.org/TR/webgpu/#lost-devices)
- Chrome 列出 adapter 為 null 的實務原因：硬體加速關閉、平台未支援、GPU 被 blocklist、無匹配 adapter、無 GPU、GPU 程序多次崩潰；`http:`／`file:` 非安全情境下 `navigator.gpu` 為 undefined。[Chrome troubleshooting](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips)

程式碼事實（本專案）：
- 產品程式沒有任何 `navigator.gpu`／WebGPU／WGSL 參照（`ticket-05/evidence/local-code-facts.txt`）。
- 主預覽 `/starlit-full-preview` → `app/starlit-sky-study/scene-study.mjs`：`canvas.getContext('webgl2', {antialias, alpha, premultipliedAlpha})`，取不到即 `onError(...)` 並回傳空清理函式；`webglcontextlost` → `fail()` → 停 rAF、`canvas.dataset.phase='failed'`、`onError`。渲染例外由 `render()` 的 try/catch 進同一 `fail`。
- `components/starlit-experience.tsx`（Ticket 02 凍結版）：失敗顯示錯誤與重試，章節內容不再被失敗遮蔽；重試重掛 canvas 走同一 WebGL2 路徑。
- 因此「不支援 WebGPU 的環境沿用 WebGL2」在現況下自然成立：現有路徑就是 WebGL2，沒有任何 WebGPU 分支。若未來加入 WebGPU，正確偵測序列為 `isSecureContext && navigator.gpu` → `await requestAdapter()` 非 null → `requestDevice()` 並掛 `device.lost` → 任一步失敗即維持現有 WebGL2 掛載（推論；未實作）。

### 5.2 程式碼事實（停頓的組成）
- `startMorph()`（`scene-study.mjs`）同步呼叫兩次 `snapshot()`：`native.snapshot` 對 240,000 表面星＋6,264 參考星各做一次 transform feedback 擷取，`prop.snapshot` 對 3,071 道具點一次，`legacy.snapshot` 對背景星一次；每次 `capture()`（`lib/fantasy-particles.mjs`）建立 TF buffer、`beginTransformFeedback` → `getBufferSubData` **同步讀回** → 刪除 buffer。
- 每份完整快照 = count × 40 B：手機 390 px 寬視窗 251,052 → 約 10.04 MB，桌面 252,364 → 約 10.09 MB；from／to 兩份約 20.1 MB 由 CPU 拼接（`Float32Array.set`）、`expandSnapshot` 迴圈重排後再 `bufferData` 上傳回 GPU。
- **粒子總數口徑（程式碼事實，`scene-study.mjs:506`、`legacy-study.mjs:80-87`、`lib/scene-pool.ts`）**：`count = native.count + legacy.skyCount`；`native.count = 240,000 + 6,264 + 3,071 = 249,335`（渲染器端，與視窗無關）；`legacy.skyCount = round(rest × 0.065)`，`rest = round(clamp(height² × 0.52 × 0.76 / 6.3, 10,000, 45,000)) + 1,600`，`height = min(canvas 高, canvas 寬 / 0.62)`。手機 390 CSS px 寬（390×844 與 390×664 皆然）→ height 629 → rest 26,421 → sky 1,717 → **251,052**（`ticket-01/evidence/prod-4g-final/result.json`、`ticket-02` 探針）；桌面 1440×900 → 上限 45,000 → rest 46,600 → sky 3,029 → **252,364**（`ticket-01/coordinator-browser/comparison.md` DOM 診斷）。兩者是**同一路徑**（`/starlit-full-preview` → `scene-study.mjs`）、同一段程式在不同視窗的結果，不是兩條路徑或兩種粒子預算；`lib/fantasy/scene.mjs:448` 使用相同公式。理論範圍 250,089（rest 下限 11,600）至 252,364（上限）。本票未改任何 count 來源，AC6「粒子數不降低」以同視窗前後相同 count 比較，不以跨視窗數字互比。
- 快照前先以 1,085,045 頂點／1.89 M 三角形的網格做一次深度遮擋 pass（`depth()`），每個一般幀也做一次。
- `getBufferSubData` 是 GL 管線的同步等待點；它佔停頓多少比例**未量測**（無 GPU timer／實機 profile）。
- 資源準備：SHA-256 逐檔驗證（`crypto.subtle`）、JPEG 解碼、`DecompressionStream` 解 gzip、JSON 解析、`bufferData` 上傳；皆與繪圖 API 無關。

### 5.3 推論：WebGPU 能與不能改善
| 項目 | WebGPU 可否改善 | 依據 |
|---|---|---|
| 30.6 MB 傳輸／58 MB 解碼、網路 RTT | 否 | 資產與網路層；與 API 無關 |
| 雜湊驗證、解碼、JSON、gzip | 否 | CPU／Web API 成本不變 |
| 章節 morph 的同步讀回 | 「可」但非必要：WebGPU 用 compute／storage buffer 可全程留在 GPU，且讀回只能走非同步 `mapAsync`（[規格 §5.2](https://www.w3.org/TR/webgpu/#buffer-mapping)）。但 WebGL2 亦可把 TF 輸出 buffer 直接綁為 morph VAO 的頂點來源、以 `bindBufferRange` 分段寫入而不讀回；`expandSnapshot` 可改為頂點著色器 gather。 | 程式碼事實＋推論；未實作、未量測 |
| 每幀 1.89 M 三角深度 pass 與 25 萬點光柵 | GPU 光柵成本不因 API 改變；WebGPU 減的是驗證／狀態切換的 CPU 開銷，本場景每幀 draw call 只有數個 | 推論；每幀 GPU 時間未量測 |
| 25 萬個 `gl_PointSize` 軟邊圓點 | 反而增加成本與風險：WebGPU point-list「A single FragmentDestination is selected within the pixel」（[規格 §23.2.5.1](https://www.w3.org/TR/webgpu/#point-rasterization)），WGSL 無 point size 內建（`spec-quotes.txt` 計數 0）；須改每粒子 4 頂點實例化四邊形（約 100 萬頂點）並重做 `gl_PointCoord` 邊緣衰減 | 規格事實＋推論 |

### 6.2 GLSL → WGSL 與管線／資源
- 語言：GLSL ES 3.00 → WGSL；`gl_VertexID`→`@builtin(vertex_index)`、`flat` 內插→`@interpolate(flat)`、`textureLod`→`textureSampleLevel`、`gl_PointSize`／`gl_PointCoord` 無對應內建值，需改實例化四邊形並自算邊緣衰減；`discard` 在 WGSL 有對應的 discard 語句（[WGSL §9.4.11](https://www.w3.org/TR/WGSL/#discard-statement)），可直接改寫或以 alpha 0 取代；WGSL uniform 佈局有對齊規則，現有以 `getUniformLocation` 逐值設定的方式改為 uniform buffer + bind group。
- 管線：blend 開／關、`depthMask`、無色輸出（深度 pass）、polygon offset（→ `depthBias`）等狀態組合各需獨立 `GPURenderPipeline`；點精靈改實例化四邊形後頂點佈局全變。
- 資源：`DEPTH_COMPONENT24` → `depth24plus` 貼圖並以 `texture_depth_2d` 取樣；WebGPU 無 `generateMipmap`（本站僅取 lod 0，可省）；canvas 走 `GPUCanvasContext.configure({alphaMode:'premultiplied'})`。
- 快照與 morph：TF 擷取 → compute pass 或 vertex→storage；`getBufferSubData` 同步 → `mapAsync` 非同步，`startMorph` 由同步狀態切換改為跨幀非同步，需重寫 `phase/transition` 狀態機與測試。
- 生命週期：`webglcontextlost` 事件 → `device.lost` promise；遺失後 API 靜默成功，需自行重建 device／pipeline／buffer 並重掛；與 Ticket 02 錯誤／重試語意對接。
- 回退與 QA：偵測失敗回 WebGL2 表示長期維護兩套渲染器；驗收矩陣加倍（WebGL2×WebGPU × 桌面×手機 × 雙語 × 章節／重播），且 AC6「粒子數不減、視覺無退步」須逐畫面對照兩套輸出。現有瀏覽器測試以 Playwright Chromium SwiftShader 執行，無頭 WebGPU 是否可用未查證。
- 依賴：專案無 three.js 等抽象層（`package.json`），遷移即手寫；本票不新增依賴。

### 6.3 成本判斷（相對，不給小時數）
- 全面遷移：大。幾乎重寫全部渲染模組與 30 段 shader、改粒子幾何模型、重做快照／morph 狀態機，並保留 WebGL2 做回退。
- 只做 WebGL2 內部的讀回移除：小到中。改動集中在 `capture()`／`createChapterMorph.set()`／`expandSnapshot` 接縫，不換 API、不動視覺。
- 以上皆推論；任何數字須以實機量測為準。

## 7. 效益證據狀態
- 本站沒有 WebGPU 實作，也沒有相同粒子數（同一視窗下同一 count，例如 390 px 寬 251,052、桌面 1440×900 252,364，§5.2）、相同相機與視覺條件下的 WebGPU vs WebGL2 比較。**因此本評估不宣稱任何 FPS、載入秒數或倍數改善。**
- 可引用的只有廠商一般性陳述：Chrome overview 稱 WebGPU「greatly reduced JavaScript workload for the same graphics」；WebKit 稱「maps better to Metal」。這些不是針對本站的量測。
- 要取得符合 AC7 的比較，需先完成 §6 大部分工作做出等價原型，再於同裝置量測；證據成本等於遷移成本本身。

## 8. 建議（連結到量測瓶頸）
1. **不在本工作包規劃全面 WebGPU 遷移。** 量測到的冷載入瓶頸是位元組與網路等待（idle 佔 profile 絕大多數），WebGPU 無關；JS long task 約 1.8 s 中的雜湊／解碼也無關。
2. **章節 morph 停頓**是唯一與 GPU 管線同步相關的候選；最短路徑是在 WebGL2 內移除 `getBufferSubData` 讀回並先在使用者手機量測前後（同粒子數、同視覺）。這是新工作，需 Coordinator／使用者決定，不屬本票。
3. **相容路徑**：維持現況即符合「不支援 WebGPU 的環境沿用 WebGL2」；不需要加任何偵測程式碼。
4. 若日後仍想評估 WebGPU，先做「最小同條件原型」：只移植星點 pass（實例化四邊形）於同一 canvas 尺寸與相同 count（該視窗量得的數字，例如手機 251,052／桌面 252,364，不得降低）粒子，量實機每幀時間，再決定是否擴大。
